# RCA — Bulk AI Generate stalls after product 1 on LIVE (glow-celesta)

Mode: READ-ONLY diagnosis. No deploy/redeploy/manifest change performed.
Deployment: glow-celesta (1ae6723c-...) · active run 6df8c119 · tier_0 · frontend_type=cloudflare · image sha256:5a6a84a1... (built by the 2026-10-23 redeploy run eb367113; the 10-27 run was a secret-only reuse of the same image).

## Problem statement
Admin "Bulk AI Generate" pasted ~23 products. Product 1 generates, product 2 never starts, "screen refreshing again and again." Never reproduced in preview (single pod, small runs finish).

## ROOT CAUSE (PRIMARY, confirmed)
The bulk worker is an **in-memory asyncio task** that dies whenever its pod restarts or is scaled down — which is exactly what happens on the live tier.

Evidence:
- Code: `routes/gift_cards_and_ai.py:2088` → `_aio.create_task(_bulk_generate_worker(job_id, body, items))`. The worker loop (lines 2108-2137) iterates items, `await _one_click_impl(...)` per item (includes Gemini image-gen + Cloudinary upload, lines 1116/1142/1155), then `await asyncio.sleep(1.0)`. The task lives only in the process memory of the one pod that received the POST.
- Live job state (Mongo `ai_jobs`, db `glow-celesta-test_database`): job `bulk_7a98a6dbf7` is **frozen** at `status:"running"`, `step:"1/23"`, `done:1`, `current:"Celesta Glow Blackhead Clearing Cream"` (product 2), `item.step:"saving product"`, `_synced_at:2026-10-28T21:12:06.345Z`.
- Pod events (run 6df8c119): pod `...-bkjq8` was killed and restarted at **2026-10-28T21:12:07** (Created/Started; image "already present"), immediately after repeated `Liveness probe failed: HTTP probe failed with statuscode: 503` (last 21:11:02) and `Startup probe failed: ...503`. The restart time matches the job's last sync to the second → the pod hosting the asyncio task was killed, the task died, the job froze forever at 1/23.

### Why the pod gets killed (the 503) — confirmed from nginx + probe logs
- nginx (platform default, `/app/scratch/nginx.conf`): the K8s probe hits `location = /health` which `proxy_pass http://127.0.0.1:8001` with **`proxy_read_timeout 1s`**. A backend 4xx is mapped to `@health_ok` (200) — that is why normal probes log `GET /health ... 404` from 127.0.0.1 (backend only defines `/api/health`, server.py:3504) yet pods stay Ready. BUT `error_page 502 503 504 = @health_error` → if the backend does not answer `/health` within **1 second**, nginx returns an error and the probe fails with 503.
- During bulk generation the event loop is tied up by the per-item image/LLM pipeline, so `/health` misses the 1s window → liveness 503 → K8s kills the pod → in-memory worker is destroyed. (The app author even notes at server.py:3788/3806 that `/health` "must return instantly" — the bulk pipeline violates that.)

### Contributing: idle scale-down + 2 replicas
- `get_tier`: tier_0, replicas 2 (max 2, HPA disabled, cpu_limit 250m, mem_limit 512Mi). Pod events show the deployment repeatedly `Scaled down ... from 2 to 1` (count 14) and back `1 to 2` (count 13) — the platform scales an "idle" replica down. If the replica running the worker is the one scaled down, the task dies the same way. CPU is clamped to 250m on tier_0, which makes the event loop more likely to miss the 1s /health window during image generation.
- The poll endpoint `GET /admin/ai/bulk-generate-job/{job_id}` (line 2094) reads via `get_job(_db, _bulk_gen_jobs, ...)` — it can serve job state from Mongo, so polling works across both replicas; but **only** the POST-receiving pod ever advances the job. Once that pod dies, no pod resumes it → "running" forever → frontend keeps polling the frozen job → perceived "not generating product 2 / screen refreshing." Brief 502/504s to the admin UI occur during the ~1 min pod-restart windows (backend down → cloudflare worker → k8s gets no upstream); these do not appear in backend logs because the backend isn't running then.

## SECONDARY bug (real, but NON-fatal — not the stall cause)
`routes/gift_cards_and_ai.py:2424` → `from services.ai_content_generator import generate_product_reviews`. That symbol does **not** exist in `services/ai_content_generator.py` (only `generate_blog_article`, `generate_location_content`). It is caught at line 2434 and logged live as:
`WARNING:routes.gift_cards_and_ai:[one-click] AI reviews failed for celesta-glow-acne-control-cream-2: cannot import name 'generate_product_reviews' from 'services.ai_content_generator'`
Effect: products are created without AI reviews. Does NOT stop the run.

## Answers to the specific questions
1. Logs (last ~24h; Loki caps at 1440 min): bulk run present — `POST /api/admin/ai/bulk-generate 200` + many `GET /api/admin/ai/bulk-generate-job/bulk_7a98a6dbf7 200`. Repeated `Started server process [23/24/25]` = repeated process (re)starts. `Unhealthy ...503` liveness/readiness/startup events. Two `[one-click] AI reviews failed ... cannot import name 'generate_product_reviews'` warnings. No OOMKilled / exit 137 in events or last_termination.
2. Backend run model: replicas=2 on tier_0 (HPA off); no explicit `--workers` in entrypoint/Dockerfile (default single uvicorn worker per pod). nginx in-pod proxies /api and /health to backend 127.0.0.1:8001. Pods DO get killed (liveness 503) and DO get scaled down 2→1 while idle.
3. 502/504: none in backend app logs for the poll or products endpoints (all logged 200/404). 503 appears on the `/health` probe path (nginx 1s read-timeout → @health_error). Client-facing 502/504 occur only during the pod-restart windows and are not captured in backend logs.
4. Products: `products` count = **157** live. `GET /api/products?active_only=false&include_variations=true` → 200 in ~871 ms (also `/health` via URL 200 in ~691ms). Not a timeout source. (The "23" is the paste list, not the DB size.)
5. Live build vs preview: live is the 2026-10-23 image (sha256:5a6a84a1...). The deployed source read in the sandbox for this run contains the `generate_product_reviews` import that doesn't resolve — the warning in live logs confirms the deployed code has this bug. Whether the user's CURRENT preview differs must be confirmed by E1 (if preview was edited after 10-23, those edits are not yet in prod).

## FIXES
- CODE (E1): Make the bulk job durable/resumable instead of a fire-and-forget `asyncio.create_task`. Options: persist the item queue in Mongo and drive it from a single resumable worker that picks up from `done`/`current` after a restart, or run generation as a proper background job/queue. Offload the CPU/sync-heavy image work (`run_in_executor`/threadpool) so `/health` keeps answering within nginx's 1s timeout and the pod isn't liveness-killed mid-run. Also fix the `generate_product_reviews` import (add the function or correct the name). Then redeploy.
- USER (interim/verify): until the code fix ships, run in small batches (2–3 items) that finish inside a probe/scale-down window, and hard-refresh the admin page; after E1's fix, redeploy. Raising the tier reduces CPU starvation but does NOT fix the design (idle scale-down 2→1 and any >1s /health stall still destroy the in-memory task), so it is not the fix.
